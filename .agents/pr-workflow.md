# PR 생성 워크플로

AI 에이전트가 완료된 작업을 검토하고 GitHub Pull Request를 생성할 때 따르는 공통 절차다.

## 적용 조건

- 사용자가 PR 생성을 명시적으로 요청했을 때 적용한다.
- 코드 또는 문서 변경이 완료되어 PR로 검토받을 수 있는 상태여야 한다.

## 진행 순서

1. 현재 브랜치, 작업 트리 상태, 기준 브랜치와의 diff, 커밋 목록을 확인한다.
2. 현재 브랜치와 연결된 이슈 및 기존 PR이 있는지 확인한다.
3. 변경 내용이 관련 이슈의 범위와 완료 기준을 충족하는지 검토한다.
4. 변경 유형에 맞는 검증 명령을 실행한다.
5. 커밋되지 않은 변경이 있으면 사용자가 직접 커밋할지, AI 에이전트가 커밋해도 되는지 확인한다.
6. push가 필요하면 사용자가 직접 수행할지, AI 에이전트가 push해도 되는지 확인한다.
7. 원격 브랜치에 최신 커밋이 반영된 것을 확인한다.
8. 최종 diff를 기준으로 PR 제목, 본문, 대상 브랜치, 연결 이슈를 포함한 초안을 사용자에게 제시한다.
9. 사용자가 초안을 승인하면 `develop`을 대상으로 PR을 생성한다.
10. 생성 결과에서 PR 번호와 URL을 확인한다.
11. 생성된 PR URL과 검증 결과를 사용자에게 알린다.

PR 초안 승인은 PR 생성만 허용하며 커밋이나 push 권한을 포함하지 않는다. AI 에이전트는 사용자의 별도 허락 없이 커밋하거나
push하지 않는다.

## 사전 확인

PR 초안을 작성하기 전에 다음 항목을 확인한다.

- 현재 브랜치가 `develop`이 아닌 작업 브랜치인지 확인한다.
- 작업 트리에 커밋되지 않은 변경이 있는지 확인한다.
- `develop`과 비교한 전체 diff와 커밋 목록을 확인한다.
- 연결할 GitHub 이슈가 존재하는지 확인한다.
- 현재 브랜치로 열린 PR이 이미 존재하는지 확인한다.
- 작업과 관련 없는 변경이나 민감한 정보가 포함되지 않았는지 확인한다.

현재 브랜치에 이미 열린 PR이 있으면 새 PR을 생성하지 않고 기존 PR을 안내한다.

작업과 관련 없는 변경이 섞여 있거나 연결할 이슈가 불명확하면 PR을 생성하기 전에 사용자에게 확인한다.

## 변경 검토

PR의 요약과 변경 사항은 사용자의 설명만으로 작성하지 않고 실제 diff와 커밋을 기준으로 작성한다.

다음 내용을 검토한다.

- 변경 목적과 관련 이슈의 요구사항
- 사용자 또는 개발자 관점에서 달라지는 동작
- 주요 구현 내용과 영향 범위
- 테스트 추가 또는 변경 여부
- 설정, 의존성, 마이그레이션 등 별도 주의사항
- 의도하지 않은 파일 변경 포함 여부

발견한 오류나 미완료 항목은 임의로 숨기거나 PR 본문에서 완료된 것으로 표현하지 않는다.

## 검증

코드 변경이 포함된 경우 다음 명령을 모두 실행한다.

- `pnpm lint`
- `pnpm typecheck`
- `pnpm test`

문서만 변경한 경우 검증을 생략할 수 있으며, PR의 `검증` 섹션에 문서만 변경되어 생략했음을 작성한다.

실행하지 않은 검증이나 실패한 검증을 완료된 체크박스로 표시하지 않는다.

검증에 실패하면 원인을 확인하고 수정 가능한 범위라면 수정한 뒤 다시 실행한다. 해결하지 못한 실패가 있으면 PR 생성 전에 사용자에게
알린다.

## PR 작성

- `.github/pull_request_template.md` 구조를 유지한다.
- 대상 브랜치는 `develop`으로 지정한다.
- 제목은 `작업 내용 요약 (#<이슈번호>)` 형식으로 작성한다.
- 제목에는 `feat:`, `fix:` 같은 Conventional Commit prefix를 붙이지 않는다.
- `관련 이슈` 섹션에 `Closes #<이슈번호>`를 작성한다.
- `요약`에는 변경 목적과 기대 효과를 간결하게 작성한다.
- `변경 사항`에는 실제 diff에서 확인한 핵심 변경을 작성한다.
- `검증`에는 실제 실행한 명령과 결과만 표시한다.
- 해당하지 않는 체크리스트는 임의로 완료 처리하지 않는다.

## 초안 승인

PR을 생성하기 전에 사용자에게 다음 정보를 포함한 초안을 제시한다.

- PR 제목
- PR 본문
- 대상 브랜치
- 작업 브랜치
- 연결 이슈
- 원격 브랜치 반영 상태
- 검증 결과

사용자의 승인을 받은 뒤에만 PR을 생성한다. 초안을 제시하기 전에 커밋과 push를 완료하므로 초안 승인 단계에서는 커밋이나 push
허락을 함께 요청하지 않는다.

승인 이후 diff나 검증 결과가 실질적으로 달라지면 변경된 내용을 알리고 다시 확인한다.

## 커밋 및 push

- 커밋되지 않은 변경이 있으면 PR 범위에 포함할 파일과 커밋 메시지를 확인한다.
- 커밋 메시지는 Conventional Commits 형식을 따른다.
- 작업과 관련 없는 파일은 커밋에 포함하지 않는다.
- Git hook이 실패하면 우회하지 않고 원인을 수정한다.
- 현재 브랜치의 원격 추적 브랜치와 로컬·원격 커밋 차이를 확인한다.
- push가 필요하면 기본적으로 사용자에게 직접 수행하도록 안내한다.
- AI 에이전트가 push해도 되는지 사용자가 명시적으로 허락한 경우에만 현재 작업 브랜치를 동일한 이름의 원격 브랜치로 push한다.
- 원격 추적 브랜치가 없고 사용자가 AI 에이전트의 push를 허락하면 `git push -u origin HEAD`로 원격 브랜치를 생성한다.
- `--force` 또는 `--force-with-lease`는 사용자가 명시적으로 요청하지 않는 한 사용하지 않는다.
- 원격 브랜치에 PR에 포함할 최신 커밋이 반영된 것을 확인한 뒤에만 PR을 생성한다.

## PR 생성

- `develop`을 base 브랜치로 지정한다.
- 현재 작업 브랜치를 head 브랜치로 지정한다.
- head 브랜치가 원격 저장소에 없거나 최신 커밋이 push되지 않았으면 PR을 생성하지 않는다.
- 승인된 제목과 본문으로 PR을 생성한다.
- 사용자가 Draft PR을 요청한 경우에만 Draft로 생성한다.
- 생성 후 PR의 번호, URL, base/head 브랜치와 본문을 확인한다.

## 실패 처리

- 검증에 실패하면 실패한 명령과 원인을 사용자에게 알린다.
- 커밋이나 push에 실패하면 PR을 먼저 생성하지 않는다.
- PR 생성에 실패하면 원격 브랜치 push 여부와 실패 원인을 알린다.
- PR은 생성됐지만 후속 확인에 실패하면 새 PR을 다시 만들지 않고 기존 PR을 조회한다.
- 실패를 우회하기 위해 검증을 생략하거나 Git hook을 비활성화하지 않는다.
