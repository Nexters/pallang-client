# 이슈 및 브랜치 생성 워크플로

AI 에이전트가 사용자의 요청을 바탕으로 GitHub 이슈를 작성하고 작업 브랜치를 생성할 때 따르는 공통 절차다.

## 적용 조건

- 사용자가 이슈 생성을 명시적으로 요청했을 때 적용한다.

## 진행 순서

1. 현재 브랜치와 작업 트리 상태, 관련 코드, 열린 이슈를 확인한다.
2. 사용자에게 어떤 작업을 시작하려는지 자연어로 질문한다.
3. 답변과 저장소에서 확인한 내용을 바탕으로 작업 유형과 범위를 판단한다.
4. 이슈 작성에 필요한 정보가 부족하면 작업 유형에 맞는 후속 질문을 한다.
5. 이슈 제목, 본문, 라벨, 담당자와 예정 브랜치명을 포함한 초안을 사용자에게 제시한다.
6. 사용자가 초안을 승인하면 현재 GitHub 인증 사용자를 담당자로 지정해 GitHub 이슈를 생성한다.
7. 생성 결과에서 이슈 번호와 URL을 확인한다.
8. 이슈 번호를 사용해 작업 브랜치를 생성하고 전환한다.
9. 생성한 이슈 URL과 브랜치명을 사용자에게 알린다.

초안 승인에는 이슈 생성, 현재 GitHub 인증 사용자의 담당자 지정, 작업 브랜치 생성과 전환이 포함된다. 승인 전에는 이슈나 브랜치를 생성하지 않는다.

## 담당자 및 브랜치 생성 예외

다음 중 하나에 해당하면 현재 사용자를 담당자로 지정하거나 작업 브랜치를 생성하기 전에 사용자의 의도를 확인한다.

- 사용자가 이슈만 등록하거나 나중에 작업하려는 의도를 표현했다.
- 다른 팀원이 작업하거나 담당자가 별도로 지정될 가능성이 있다.
- 아이디어, 백로그 또는 논의 사항을 기록하기 위한 이슈다.
- 현재 작업 트리 상태 때문에 바로 브랜치를 생성하거나 전환하기 어렵다.

필요한 경우 이슈만 생성할지, 현재 사용자를 담당자로 지정하고 브랜치까지 생성할지 질문한다. 사용자가 이슈만 생성하도록 요청하면 담당자를 임의로 지정하거나 작업 브랜치를 생성하지 않는다.

## 요구사항 수집

사용자의 요청과 저장소에서 확인한 내용을 활용해 이슈 템플릿을 간결하게 채운다. 모든 항목을 설문처럼 질문하지 않고, 이슈의 작업 내용이나 완료 기준을 작성할 수 없을 때만 필요한 내용을 짧게 추가로 질문한다.

작업 유형별로 다음 항목을 작성한다.

- 기능 요청: `배경`, `요구사항`, `완료 기준`
- 버그 리포트: `문제`, `재현 방법`, `기대 동작`, `실제 동작`, 필요한 경우 `환경`
- 일반 작업: `작업 내용`, `완료 기준`
- 참고 자료는 실제로 제공됐거나 저장소에서 관련 자료를 찾은 경우에만 작성한다.

추가 질문은 다음과 같이 이슈 작성에 꼭 필요한 정보로 제한한다.

- 기능 요청은 구현할 기능이나 완료 기준이 불명확한 경우에만 질문한다.
- 버그 리포트는 문제를 재현하거나 기대 동작을 판단할 수 없는 경우에만 질문한다.
- 일반 작업은 변경 대상이나 기대 결과가 불명확한 경우에만 질문한다.

제외 범위나 가정 같은 추가 섹션은 작업 범위를 오해할 가능성이 클 때만 사용한다. 확인되지 않은 내용을 임의로 확정하지 않으며, 하나의 이슈로 다루기 어려울 만큼 범위가 크면 이슈 분리안을 먼저 제안한다.

## 이슈 작성

- 작업 유형에 맞는 `.github/ISSUE_TEMPLATE` 구조를 사용한다.
- 제목은 `<prefix>: <작업 요약>` 형식으로 작성한다.
- 본문의 템플릿 섹션을 유지하고, 필요한 경우 `제외 범위`와 `가정`을 추가한다.
- 완료 기준은 결과를 확인할 수 있는 체크박스로 작성한다.
- 코드 변경에는 `pnpm lint`, `pnpm typecheck`, `pnpm test` 통과를 완료 기준에 포함한다.
- 기본적으로 현재 GitHub 인증 사용자를 담당자로 지정한다. GitHub CLI에서는 `--assignee "@me"`를 사용한다.
- 저장소에 존재하지 않는 라벨을 임의로 생성하지 않는다.

## 작업 유형과 라벨

| 작업 성격                 | 템플릿               | 제목 prefix | 라벨          | 브랜치 유형 |
| ------------------------- | -------------------- | ----------- | ------------- | ----------- |
| 기능 추가·개선            | `feature_request.md` | `feat`      | `✨ feature`  | `feat`      |
| 버그 수정                 | `bug_report.md`      | `fix`       | `🐞 bug`      | `fix`       |
| 리팩터링                  | `task.md`            | `refactor`  | `🔨 refactor` | `refactor`  |
| 문서                      | `task.md`            | `docs`      | `📃 docs`     | `docs`      |
| 설정·의존성·기타 유지보수 | `task.md`            | `chore`     | `⚙️ chore`    | `chore`     |
| 배포                      | `task.md`            | `deploy`    | `🌏 deploy`   | `deploy`    |

여러 작업 유형이 포함되면 이슈의 주된 목적을 기준으로 템플릿, 제목 prefix와 브랜치 유형을 결정한다. 부수 작업도 독립적인 결과물
로 중요하면 해당 라벨을 추가할 수 있다.

## 브랜치 생성

- 이슈 생성이 성공하고 반환된 번호를 확인한 뒤에만 브랜치를 만든다.
- 브랜치 형식은 `<유형>/<이슈번호>-<kebab-case-slug>`를 사용한다.
- 예: `feat/42-login-form`, `fix/57-login-redirect`
- 슬러그는 영문 소문자, 숫자와 하이픈만 사용하며 작업의 핵심을 짧게 표현한다.
- 작업 트리에 기존 변경이 있으면 이를 보존하고 안전하게 전환할 수 있는지 먼저 확인한다.
- 이슈 번호를 추측하거나 로컬 전용 임시 번호를 만들지 않는다.

## 실패 처리

- GitHub 인증, 권한 또는 네트워크 문제로 이슈 생성에 실패하면 브랜치를 먼저 만들지 않는다.
- 이슈는 생성됐지만 브랜치 생성에 실패하면 생성된 이슈 URL과 실패 원인을 사용자에게 알린다.
- 실패를 우회하기 위해 존재하지 않는 이슈 번호나 라벨을 사용하지 않는다.

## PR 연결

- PR은 `main`을 대상으로 생성한다.
- PR 제목은 `작업 내용 요약 (#<이슈번호>)` 형식으로 작성한다.
- PR 본문의 관련 이슈 섹션에 `Closes #<이슈번호>`를 포함한다.
